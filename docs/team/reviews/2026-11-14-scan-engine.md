## First review of the scan engine (research scientist, 2026-11-14)

I edited no files. I read the spec v1, plan-v2, the wdv2 branch code and the six main files you named. I checked the facts below against their sources. I did not run the game. These are findings from review only.

**What the spec gets right**
- Every channel has a rule fallback (spec §1.3, §4). A missing eye only lowers confidence. This is what lets the scan work at a random US place.
- Lidar wins for heights (§5.2). Seeds come from OSM ids or a quantised position (§1). `SimCruiseCellContext.cpp:156-161` already does this correctly.
- `META` records sources, licences, eye versions and error per channel (§3). The Python lab writes the same channels and the same file (§4). This lets us test a model before it goes into C++.

**Experiments to run first** (all held out from fusion; 18 places from `data/test-places.json`)
1. Canopy and crowns. Data: 1 km² at the 16 places with 3DEP lidar. Truth: lidar canopy model (first return minus bare earth) at 1 m. Metrics: canopy IoU (> 2 m), height RMSE and bias, crown F1 (match ≤ 3 m). Pass: IoU ≥ 0.75, RMSE ≤ 3 m, |bias| ≤ 1 m, F1 ≥ 0.6. Report Hilo and Anchorage separately.
2. De-lighting and albedo. Data: 1 km² at 6 places (desert, farm, city, forest, coast, Alaska). Truth: HLS summer median surface reflectance at 30 m. Metrics: per-band bias and RMSE of the de-lit albedo averaged to 30 m, shade/lit ratio per class. Pass: |bias| ≤ 0.02, RMSE ≤ 0.04, shade/lit ≥ 0.85, ≥ 90 % of class patches inside the published range (grass 0.08-0.25, asphalt 0.05-0.12, concrete 0.25-0.35).
3. Surface classes, buildings and time. Data: 200 stratified random points per place (3600 in total), hand-labelled on NAIP (Congalton and Green 2019), plus held-out footprints. Metrics: overall accuracy, F1 per class, building F1, CPU time per tile at p95. Pass: overall accuracy ≥ 0.86 at level I (NLCD 2021 gets 81 % ± 0.9, USGS pubs 70275777), building F1 ≥ 0.90 (Microsoft footprints: precision 98.5 %, recall 92.4 %), all eyes ≤ 3 s per tile on 2 cores.

**Short advice for the world thread**
- Trust order for heights: 3DEP lidar (1 m, public domain) > CHMv2 (CC BY 4.0, MAE 1.4 m) > LANDFIRE height > rules.
- Trust order for land cover: new NAIP plus NIR eye > OSM and Microsoft footprints > NLCD 2021 (73 % at level II) > LANDFIRE EVT (about 47 % per type) > Köppen rules. Lower trust when a source is older than the photo.
- Make de-lighting a helper step on every tile, fitted to HLS reflectance. The 4 Miami files are a demo, not the method.
- Do not ship CHMv2's DINOv3 model or DeepForest's 10 cm weights as they are. Use the CHMv2 map as data, and a small student of Satlas (ODC-BY) as the eye.
- Rock and soil on cuts: there is no legal CPU model for this. Use rules: lidar slope + USGS SGMC geology + gSSURGO Munsell soil colour (public domain; whether gSSURGO has the colour field is my estimate, check it) + NAIP colour.
- Look ahead by distance (≥ 600 m along the heading), not by tile ring. Anchorage tiles are 294 m wide.
- Prove each channel on held-out data at random places, never only with the self-check.

## First review of the scan engine (applied mathematician, 2026-11-14)

I read the role file and notes, the charter, scan-map-spec.md v1, plan-v2.md, the wdv2 branch (plan, SimCruiseCellContext.h/.cpp, tests), and on main: SimCruiseWorldResources.cpp, SimCruiseGeo.cpp, SimCruiseRoadNetwork.cpp, SimCruiseTileBuilder.cpp, SimCruiseWorldTile.cpp and helper/road-grade.mjs. I changed no files. All findings come from reading code and doing arithmetic. I did not run the game.

**What the spec gets right**
- The scan is keyed to the z16 tile, and seeds come from OSM ids, never from row order (spec §1, §2). The Web Mercator z16 tiles are already a fixed global grid, so this is the right grid to align to.
- Each channel has a rule fallback, and a failed eye only lowers confidence (§4). This meets charter rule 5 where map data is poor (Welch WV, Hilo).
- The fusion priority puts measured data first: map geometry, then lidar heights, then eyes, then rules (§5). The road profile is a robust Gaussian local-linear fit with a Tukey pass (road-grade.mjs:198-230; RoadNetwork.cpp:793-804). This is a sound base for the road-step check.
- The detail kit already uses a variance-preserving hex blend (WorldResources.cpp:150-160). This is the Gaussian form of Heitz and Neyret (HPG 2018) and Burley (JCGT 8(4), 2019).

**Short advice for the world thread**
- Fix the 64 m texture anchor first. It makes seams at every tile border today (all periods except divisors of 64 m). Add a seam unit test.
- Make the scan grid 512 cells per z16 tile plus an 8-cell guard. Identify cells by global uint z25 ids. Never store or hash "world metres".
- Take seeds and 32 m stations from the OSM way's own geodesic arc length, not from tile tangents or session-dependent Side.
- Store the class as top-2 plus a weight, with histogram mips and a Gather in the shader. Never filter enum ids.
- Replace sin hashes with pcg2d on uint (JCGT 2020). Add a small domain warp at class edges.
- Self-check: register first (phase correlation), render class means on held-out cells, and score per-class ΔE00 and SSIM with a Huber fit. Calibrate the pass line on all 18 test places.
- Redefine the road step as the deviation from the fitted grade (≤ 2 mm per 0.5 m, estimate). Scan D = v·(T_fetch + T_eyes + T_upload + 4 s) beyond the view distance, with 2 workers so ρ < 0.7. Cross-fade a late scan over 1 s (no pop-in).
